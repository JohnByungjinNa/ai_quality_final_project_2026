# Task 1 검토 가이드

- 목적: KPI·SLO·화면 범위를 구현 전에 한 번에 확인한다.
- 현재 상태: `APPROVED`
- 승인 내용: 권장안 1~5, 일 예산 50,000 KRW, 화면 배치, 전체 상태 우선순위
- 추가 조건: 기존 대시보드를 유지한 채 새 종합 상황판을 별도 화면으로 추가
- 기준 문서: `docs/ai_qa_dashboard_kpi_spec.md`

## 1. 제안 화면 배치

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ AI QA 종합 상황판       기간 | 환경 | 서비스 | 공급자 | 모델 | 마지막 갱신 │
├───────────┬───────────┬───────────┬───────────┬───────────┬───────────────┤
│ 품질점수  │ 통과율    │ p95       │ 오류율    │ 안전위반  │ API 비용      │
├───────────────────────┬───────────────────────┬─────────────────────────────┤
│ 품질 점수 추이        │ 테스트 PASS/FAIL/ERROR│ 운영 상태·핵심 경고          │
├───────────────────────┼───────────────────────┼─────────────────────────────┤
│ 품질 지표별 점수      │ 단계별 응답시간       │ RAG 검색 품질                │
├───────────────────────────────────────────────┬─────────────────────────────┤
│ 최근 실패 테스트·결함                         │ 알림·권장 조치                │
└───────────────────────────────────────────────┴─────────────────────────────┘
```

구현 시 상단 KPI는 작은 화면에서 자동 줄바꿈되는 가로 컨테이너를 사용하고, 각 카드는 숫자·전 기간 대비 변화·짧은 추이를 함께 표시한다. 상세 표는 내부 ID와 민감 정보가 화면에 전달되지 않도록 조회 단계에서 제거한다.

## 2. 계산 예시

샘플 데이터:

| 항목 | 값 |
|---|---:|
| accuracy 평균 | 4.8 / 5 |
| groundedness 평균 | 4.5 / 5 |
| helpfulness 평균 | 4.6 / 5 |
| safety 평균 | 4.9 / 5 |
| PASS / FAIL / ERROR | 237 / 12 / 1 |
| p95 응답시간 | 3.1초 |
| 5xx + timeout / 전체 요청 | 4 / 250 |
| High 안전성 위반 | 1건 |
| 오늘 비용 / 일 예산 | 18,420원 / 30,000원 |

계산 결과:

| KPI | 계산 | 표시 상태 |
|---|---|---|
| 전체 품질점수 | ((4.8 + 4.5 + 4.6 + 4.9) ÷ 4) ÷ 5 × 100 = 94.0점 | 정상 |
| 테스트 통과율 | 237 ÷ 250 × 100 = 94.8% | 주의 |
| p95 응답시간 | 3.1초 | 정상 |
| 서비스 오류율 | 4 ÷ 250 × 100 = 1.6% | 주의 |
| 안전성 위반 | 1건 | 위험 |
| API 비용 | 18,420 ÷ 30,000 × 100 = 61.4% | 정상 |

전체 품질점수가 94점이어도 안전성 위반이 1건 있으므로 `전체 운영 상태`는 위험으로 표시한다. 평균점수는 원인을 숨기지 않도록 개별 KPI 상태를 덮어쓰지 않는다.

## 3. 상태 우선순위

1. 안전성 High/Critical 위반이 1건 이상이면 전체 상태는 `위험`이다.
2. 데이터 신선도가 위험이면 해당 지표는 수치 대신 `수집 지연` 상태를 우선 표시한다.
3. 하나 이상의 핵심 KPI가 위험이면 전체 상태는 `위험`이다.
4. 위험은 없지만 하나 이상의 핵심 KPI가 주의이면 전체 상태는 `주의`다.
5. 모든 핵심 KPI가 정상이고 데이터가 최신이면 전체 상태는 `정상`이다.
6. 필수 데이터가 한 번도 수집되지 않았으면 전체 상태는 `판정 불가`다.

## 4. 데이터 없음 표시 예시

| 상황 | 카드 표시 | 상태 |
|---|---|---|
| 조회 기간에 요청이 없음 | 데이터 없음 | 판정 불가 |
| LLM usage 계측 전 | 데이터 없음 | 계측 필요 |
| 비용은 추정치만 존재 | 추정 11.67원 | 추정 배지 표시 |
| 마지막 수집이 15분 초과 | 마지막 정상값과 수집 시각 | 수집 지연 |
| 분모가 0인 비율 | 데이터 없음 | 0%로 계산하지 않음 |

## 5. 구현 시 적용할 Streamlit 원칙

- KPI 카드는 기본 `st.metric(..., border=True)`와 짧은 추이 데이터를 사용한다.
- KPI 행은 작은 화면에서 줄바꿈 가능한 `st.container(horizontal=True)`를 사용한다.
- 상세 영역은 `st.container(border=True)`로 구분한다.
- 단순 추이는 Streamlit 기본 차트, 다중 시리즈·툴팁이 필요한 경우 Altair를 사용한다.
- 원천 데이터 로딩은 캐시하고, 독립 영역의 자동 갱신은 fragment 단위로 분리한다.
- 새 코드에는 폐기 예정인 `use_container_width`를 사용하지 않는다.

## 6. Codex와 사용자 역할

Codex가 하는 일:

- 승인 결과를 KPI 정의서와 로드맵에 확정본으로 반영한다.
- 승인된 지표가 이후 이벤트 스키마·집계 API·화면에서 같은 의미를 유지하도록 추적한다.
- 계산식과 경계값을 자동 테스트로 검증한다.

사용자가 하는 일:

- KPI 정의서의 권장안 1~5 승인 여부를 결정한다.
- 일 API 비용 예산을 지정한다.
- 위 화면 배치와 전체 상태 우선순위에 수정이 필요한지 알려준다.
