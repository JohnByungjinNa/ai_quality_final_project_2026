# VOC AI 품질관리 포트폴리오 발표 구성안

권장 발표 시간은 8~10분이며, 이후 3~5분 동안 시연 영상을 보여주는 구성입니다.

## 1장. 표지

**제목**

AI 기반 VOC 개선안 타당성 평가 및 품질 승인 플랫폼

**부제**

Multi-Agent Pipeline과 독립 LLM Judge를 활용한 근거 기반 AI QA

**화면 구성**

- 프로젝트명, 작성자, 기간과 역할
- Agent 관리 화면 또는 최종 승인 화면
- 하단에 GitHub·시연 영상 QR 또는 링크

**발표 멘트**

> 고객 VOC를 분석하는 AI는 많지만, 생성된 개선안을 실제 운영에 적용해도 되는지 검증하는 시스템은 부족합니다. 이 프로젝트는 VOC 근거 수집부터 타당성 평가와 사람 승인까지 하나의 품질 프로세스로 연결했습니다.

## 2장. 문제 정의

**핵심 메시지**

좋아 보이는 AI 답변과 실행 가능한 개선안은 다르다.

**내용**

- 생성 결과의 VOC 근거와 Trace를 확인하기 어려움
- 생성 모델이 스스로 평가할 때 발생하는 편향
- 담당·일정·KPI·위험이 빠진 개선안
- AI PASS와 실제 운영 책임의 혼동
- 여러 도구에 흩어진 실행·승인·증적

**발표 멘트**

> 답변이 자연스럽고 점수가 높더라도 담당자와 일정, 측정 지표, 위험 대응이 없다면 실제 개선으로 이어질 수 없습니다. 그래서 이 프로젝트의 중심을 답변 생성보다 타당성 검증에 두었습니다.

## 3장. 프로젝트 목표

**핵심 문구**

그럴듯한 개선안이 아니라, 실행하고 측정하며 책임질 수 있는 개선안만 운영으로 연결한다.

**세 가지 목표**

1. 근거 연결: VOC 원문·Run·Case·Trace로 판단 재현
2. 실행 가능성: 담당·일정·KPI·적용 범위·위험 검증
3. 책임 있는 적용: QA와 업무 승인을 분리해 책임 확정

**화면 구성**

세 개의 카드 또는 삼각형 구조로 표현합니다.

## 4장. 전체 품질 프로세스

**흐름**

`VOC → 6 Agent → 독립 Judge → 타당성 평가 → QA 검토 → 업무 승인 → 운영 증적`

**강조할 내용**

- 단계별 결과와 실패 상태를 별도로 저장
- 미달 단계에서는 보완·RETEST로 회귀
- AI 자동 통과만으로 정식 승인하지 않음

**발표 멘트**

> 각 단계는 단순 화면 순서가 아니라 다음 단계 진입 조건을 가진 품질 Gate입니다. 오류나 미검증 상태를 성공으로 바꾸지 않고 그대로 보존합니다.

## 5장. 시스템 아키텍처

**화면 구성**

- 왼쪽: Streamlit과 품질 서비스
- 가운데: gRPC Orchestrator와 6개 Agent
- 오른쪽: 독립 Judge, 타당성 평가, Run 증적
- 하단: Jira·GitHub·AWS

**기술 포인트**

- 6101~6106 포트의 독립 Agent 프로세스
- Summarizer 중심의 단일 Pipeline 오케스트레이션
- Provider별 LLM 역할 분리
- Run·Case·Trace 파일 기반 증적 저장

## 6장. Multi-Agent Pipeline

**Agent 역할**

- Interpreter: 의도와 검색 조건 해석
- Retriever: VOC 원문 검색
- Summarizer: 요약 후보 생성과 흐름 제어
- Evaluator: 후보 상대평가
- Critic: 누락·모순·위험 검토
- Improver: 정책 개선안 생성

**추천 이미지**

`.artifacts/demo/02-agent-management.png`

**발표 멘트**

> Agent를 많이 만든 것이 핵심이 아니라 책임과 증적을 분리한 것이 핵심입니다. 어떤 단계에서 어떤 판단이 이뤄졌는지 Trace로 확인할 수 있습니다.

## 7장. 독립 LLM Judge

**핵심 메시지**

Pipeline 내부 평가와 최종 평가를 분리해 자기평가 편향을 줄였다.

**내용**

- 별도 Provider·모델 선택
- 100점 Rubric과 차원별 근거
- Provider 조합 기반 독립성 등급
- Pipeline 상태와 Judge 상태 분리

**시연 근거**

- 최초 동일 계열 평가: 91점, 독립성 C, 검토 필요
- Provider 분리 후 평가: 96점, 독립성 A, PASS

## 8장. 핵심 차별점 — 개선안 타당성 평가

**강조 문구**

품질이 좋은 답변인지가 아니라, 실제로 실행해도 되는 개선안인지 평가한다.

**평가 차원**

- 원인과 개선안 연결 22점
- VOC·Trace 근거 22점
- 업무·기술 실행 가능성 18점
- 담당·일정·KPI 13점
- 위험·보안·규제 25점

**설계 포인트**

- 모델의 총점·판정을 서버가 재계산
- 항목별 하한과 즉시 보류 규칙
- 초안작성 마법사로 근거 입력 보완
- `AI_PASS → QA_REVIEWED → BUSINESS_APPROVED`

## 9장. 증적과 결함관리

**내용**

- Run·Case·Trace·Rubric 버전과 해시
- 독립 Judge와 타당성 평가 원본 결과
- QA·업무 승인 append-only 감사 이력
- 결함 `OPEN → ANALYZED → FIXED → RETESTED → CLOSED`
- 기준 Run과 연결 RETEST만 A/B 비교

**발표 멘트**

> 개선됐다는 주장보다 동일 조건의 증적이 먼저입니다. 조건이 다른 Run은 비교를 차단하고, 연결된 재시험이 통과해야 결함을 종료할 수 있습니다.

## 10장. Jira·GitHub·AWS 연동

**Jira**

- JQL 이슈 조회, 선택적 이슈 등록, 등록 감사 이력

**GitHub**

- 저장소·브랜치·커밋 상태, 프로젝트 저장·다운로드, 충돌 사전 점검

**AWS**

- 최종 인수 JSON·Markdown 증적만 S3 업로드
- 비밀값 패턴·파일 크기 검사와 AES256
- 매니페스트 및 원격 SHA-256 검증

**안전 원칙**

외부 변경은 사용자의 명시적 버튼 동작에서만 수행합니다.

## 부록. 예상 질문

### 왜 Multi-Agent로 구성했나요?

한 모델의 긴 Prompt로 모든 일을 처리하기보다 검색, 평가, 비평과 개선 책임을 분리해 단계별 실패 원인과 증적을 확인하기 위해서입니다.

### 독립 Judge만 있으면 충분하지 않나요?

Judge는 답변 품질을 평가하지만 담당·일정·KPI와 실제 업무 위험까지 보장하지 않습니다. 그래서 실행 타당성 Gate를 별도로 두었습니다.

### AI_PASS인데 왜 사람 승인이 필요한가요?

자동 평가는 기준 충족 여부를 판단하지만 실제 적용 범위와 책임을 질 수 없습니다. QA는 품질 근거를, 업무 담당자는 운영 적용 가능성과 책임 범위를 승인합니다.

### 35건 전체가 승인된 프로젝트인가요?

아닙니다. 대표 TC-01의 E2E 승인 흐름은 완료됐지만 기존 35건 운영 인수 Run은 HOLD입니다. 두 결과를 분리해 관리하고 있습니다.

### 생성형 AI의 잘못된 판정은 어떻게 막았나요?

모델이 반환한 총점과 판정을 서버에서 차원별 점수로 재계산하며, 근거 누락·안전·중요 결함·Judge 상태는 서버 규칙으로 강제합니다.
