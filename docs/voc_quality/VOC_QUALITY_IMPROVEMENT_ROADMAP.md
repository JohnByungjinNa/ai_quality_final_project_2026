# VOC 품질진단 고도화 로드맵

## 1. 목적

이 문서는 VOC 품질진단을 다음 수준으로 고도화하기 위한 변경 가능한 기준선이다.

- 멀티 에이전트가 단순히 실행되는지를 넘어 실제 VOC 근거로 정확하고 안전한 정책 개선안을 만드는지 검증한다.
- Evaluator·Critic의 파이프라인 내부 평가와 독립 LLM Judge의 외부 평가를 구분한다.
- 기존 답변과 개선 답변을 동일 Rubric으로 A/B 평가해 배포 가능 여부를 판단한다.
- 테스트 실행, Trace, Judge, 결함, 재시험, 사람 승인과 보고서를 하나의 실행 이력으로 추적한다.
- 동료평가 80점과 교수평가 20점의 모든 항목을 재현 가능한 품질 증적으로 연결한다.

로드맵은 확정 후에도 변경할 수 있다. 다만 진행 중인 Step의 완료 기준에 영향을 주는 변경은 해당 Step에서 먼저 반영하고, 이후 Step의 변경은 백로그에 추가한다.

## 2. 단계 운영 규칙

### 상태

- `WAITING`: 앞 단계가 완료되지 않아 대기
- `READY`: 착수 가능한 다음 단계
- `IN_PROGRESS`: 현재 구현·정교화 중인 유일한 단계
- `USER_REVIEW`: 구현과 자동 검증이 끝나 사용자 보완·승인 대기
- `COMPLETE`: 사용자 확인과 완료 증적 기록까지 종료
- `BLOCKED`: 외부 키·서비스·의사결정 없이는 진행할 수 없음

### 한 Step의 진행 순서

1. 범위와 완료 기준 확인
2. 설계안 또는 화면 초안 확인
3. 기능 구현
4. 자동 테스트와 실제 화면 검증
5. 사용자의 기능 확인 및 추가 보완
6. 완료 승인
7. 로드맵·Notion 증적 갱신 후 다음 Step을 `READY`로 전환

한 번에 하나의 Step만 `IN_PROGRESS`로 둔다. 사용자가 현재 Step의 보완을 요청하면 다음 Step으로 넘어가지 않고 현재 Step에 반영한다.

### 공통 완료 조건

모든 Step은 다음 조건을 충족해야 완료할 수 있다.

- 기능과 예외 처리 구현
- 관련 자동 테스트 PASS
- 기존 VOC 수동 실행과 Agent Pipeline 회귀 없음
- 비밀값·VOC 원문·개인정보의 불필요한 저장 없음
- 실행 방법과 결과 위치 문서화
- `VS Code > VOC_Improve`에 구현·검증 결과 기록
- 사용자 완료 확인

## 3. 현재 기준선

### 확인된 구현

- 6개 Agent와 gRPC Pipeline
- 20개 VOC 테스트케이스 정의
- 수동 TC 선택 실행과 실시간 Agent Pipeline
- A2A Trace와 핵심 키워드·처리시간 기록
- 6종 격리 장애 시험
- 100점 시스템 품질 Rubric
- VOC 실행 결과 JSON·Markdown 저장과 Report 조회
- 일반 테스트 관리의 실행·이력·상세·삭제 화면
- 일반 품질 보고서용 HTML/PDF 생성 기반

### 신규 구현 또는 확장이 필요한 항목

- VOC 테스트케이스 일괄 실행
- VOC 전용 수행 이력과 실행 단위 증적 저장
- 수동·일괄 실행 시 독립 LLM Judge와 Provider 선택
- 최종 개선안의 자동 타당성 검사와 사람 승인
- 결함과 재시험의 수명주기 연결
- 35건 기준 정량 분석과 A/B 비교
- TXT·XML·HTML 최종 품질 증적
- VOC 전용 품질 보고서 메뉴
- README 기반 사용자 매뉴얼 메뉴

### 반드시 먼저 바로잡을 사실

- 현재 독립 LLM Judge 실행은 구현되지 않았다.
- 현재 Improver는 Claude 계열 모델을 사용할 수 있으므로, Judge를 추가할 때 생성 모델과 Judge 모델·Provider의 독립성 등급을 별도로 기록해야 한다.
- 저장소의 VOC 기능 테스트케이스는 현재 20건이다. 보고서의 `전체 35건`, `초기 33 PASS / 2 FAIL`, `최종 35 PASS`는 동일한 테스트 ID와 실행 증적을 연결한 뒤에만 확정 수치로 사용한다.
- 기존 OpenAI 기반 `judge_agent.py`는 교육과정 챗봇 평가용이므로 VOC 독립 Judge에 그대로 사용하지 않고 공통 패턴만 재사용한다.

## 4. 제안 메뉴 구조

`홈 > VOC 품질진단` 아래 메뉴를 최종적으로 다음과 같이 정리한다.

1. Dashboard
2. 수동 TC 수행
3. 일괄 TC 수행
4. 수행 이력
5. 개선안 타당성 검증
6. 품질 보고서
7. Agent 관리
8. VOC 분석
9. 테스트케이스
10. 품질 평가 기준
11. 장애·결함 관리
12. A2A Trace
13. 사용자 가이드

LLM Judge는 별도 실행 메뉴로 분리하지 않고 수동 TC와 일괄 TC의 실행 옵션으로 제공한다. Judge Rubric과 모델 독립성 기준은 `품질 평가 기준`에서 관리한다.

## 5. 35건 테스트 구성 초안

35건은 다음처럼 하나의 품질 세트로 구성하는 안을 Step 1에서 확정한다.

| 구분 | 건수 | 현재 상태 | 목적 |
|---|---:|---|---|
| VOC 기능·경계 테스트 | 20 | 정의 완료 | 정상·모호·복합·무검색·오타·장애 질문 검증 |
| 격리 장애 테스트 | 6 | 구현 완료 | Agent 중단·포트·CSV·API 키·지연·빈 결과 검증 |
| Agent 역할 품질 테스트 | 6 | 신규 | Interpreter부터 Improver까지 역할별 품질 검증 |
| 종합 품질 게이트 | 3 | 신규 | A2A 완전성·독립 Judge·최종 타당성 및 배포 판정 |
| 합계 | 35 | 확정 필요 | 동일 ID로 기준선과 재시험 비교 |

35건의 최종 구성은 사용자가 보유한 기존 35건 목록이 있으면 그 목록을 우선한다. 위 표는 누락된 목록을 보완하기 위한 초안이다.

## 6. 평가자 역할 구분

| 평가자 | 위치 | 평가 대상 | 역할 | 최종 승인 권한 |
|---|---|---|---|---|
| Evaluator | Pipeline 내부 | 복수 요약 후보 | 상대 비교와 후보 선택 | 없음 |
| Critic | Pipeline 내부 | 선택 요약·정책 | 누락·모순·수정 필요사항 검토 | 없음 |
| 독립 LLM Judge | Pipeline 외부 | 최종 요약·개선안 | 정확성·근거성·충실성·구체성·안전성의 독립 채점 | 자동 품질 게이트만 판단 |
| QA 검토자 | 사람 | 실행 결과·Trace·Judge | 시험 적정성, 결함, 재시험 확인 | 품질 승인 의견 |
| 업무·시스템 담당자 | 사람 | 최종 정책 개선안 | 원인 연결성, 실행 가능성, 운영 영향 검토 | 운영 적용 승인 |

기술적 파일럿 배포와 정식 품질 승인을 구분한다. Agent 실행 성공만으로 정식 승인하지 않는다.

## 7. 실행·증적 데이터 구조 초안

VOC 실행은 실행 ID 하나로 모든 증적을 연결한다.

```text
reports/voc_quality_runs/<run_id>/
  manifest.json              # 실행 설정, 모델, Rubric 버전, 대상 TC
  summary.json               # 전체 PASS/FAIL, 성공률, 시간, 비용
  cases/<case_id>/
    pipeline_result.json     # 요약·정책 개선안
    trace.json               # Agent 흐름과 안전한 전달 데이터
    rule_result.json         # 구조·금지값·기대 요소 평가
    judge_result.json        # 독립 LLM Judge 결과
    validity_result.json     # 자동·사람 타당성 검토
  defects.json               # 결함과 재시험 연결
  evidence/result.txt
  evidence/junit.xml
  evidence/report.html
```

중앙 이력 인덱스에는 실행 ID, 실행 시각, 실행 유형, 대상 수, PASS/FAIL/ERROR, Judge 사용 여부, 배포 판정, 실행 폴더만 저장한다. 질문 원문과 전체 LLM 응답은 필요한 실행 증적 폴더에만 최소 보존하고 목록·Prometheus label에는 저장하지 않는다.

## 8. 단계별 로드맵

### Step 0. 로드맵 기준선 수립 — `COMPLETE`

목표:

- 발표 평가 기준과 요구 기능을 구현 순서로 구조화한다.
- 한 단계씩 완료·승인 후 이동하는 관리 규칙을 만든다.

완료 증적:

- 이 로드맵 문서
- 평가 항목 추적표
- 현재 구현·미구현 구분

### Step 1. 품질 기준·35건 테스트·증적 계약 확정 — `COMPLETE`

목표:

- 이후 모든 구현이 공유할 테스트 ID, 점수, PASS/FAIL, 실행 이력 계약을 확정한다.

구현·정교화 항목:

- 35건 테스트 구성과 ID 확정
- 현재 20개 테스트케이스와 6개 장애 시험 매핑
- 6개 Agent 역할 품질 기준과 종합 게이트 3건 정의
- 독립 Judge Rubric 초안 확정
- 개선안 타당성 Rubric 초안 확정
- `품질 평가 기준` 메뉴에서 내부 Pipeline·독립 LLM Judge·개선안 타당성 기준을 분리 조회·수정·업로드
- VOC 신규 페이지는 상단 메뉴 경로와 중복되는 별도 페이지 제목을 두지 않음
- `PASS`, `FAIL`, `ERROR`, `NOT_RUN`, `REVIEW_REQUIRED` 의미 확정
- 기준선 실행과 재시험이 같은 TC인지 보장하는 버전·해시 규칙 정의
- 33 PASS / 2 FAIL 기준선과 결함 2건의 실제 증적 확인

제안 Judge 100점 초안:

- 정확성 25
- 근거성 25
- 충실성 20
- 구체성 15
- 안전성 15

제안 타당성 100점 초안:

- 불만 원인과 개선안 연결 25
- VOC·Trace 근거 추적성 20
- 업무·기술 실행 가능성 20
- 담당·일정·KPI 구체성 20
- 위험·보안·규제 고려 15

완료 조건:

- 35건 목록과 기대 결과가 파일로 존재
- 평가 스키마와 상태값 자동 검증 PASS
- 세 가지 100점 기준이 같은 메뉴에서 책임과 후속 실행 Step을 구분해 표시됨
- 33/2 기준선 수치의 원본 증적 또는 대체 기준선 확정
- 사용자 승인

### Step 2. VOC 실행 세션·수행 이력 저장 기반 — `COMPLETE`

목표:

- 수동·일괄·Judge·보고서가 공유하는 영속 실행 모델을 구현한다.

구현 항목:

- 실행 ID와 실행 manifest 생성
- 실행별 폴더·케이스별 결과 저장
- 중앙 이력 인덱스와 원자적 저장
- 중단·오류 후 불완전 실행 복구 표시
- 모델·프롬프트·Rubric·TC 버전 스냅샷
- 비밀값·개인정보 마스킹과 보존 정책

완료 조건:

- 수동 TC 1건 실행이 새 구조로 저장됨
- 앱 재시작 후 이력 복원
- 손상 파일·중복 ID·부분 실행 테스트 PASS

### Step 3. 테스트케이스 일괄 실행 — `COMPLETE`

목표:

- 여러 TC 또는 전체 품질 세트를 안전하게 실행하고 진행률을 확인한다.

구현 항목:

- `일괄 TC 수행` 메뉴
- 전체·분류·개별 다중 선택
- 실행 전 Agent·환경·모델 점검
- 기본 순차 실행, 중지, 미수행 표시, 실패 재실행
- 케이스별 진행 상태와 전체 진행률
- 429 backoff, timeout, 재시도 횟수와 실패 원인 기록
- 실행 완료 후 수행 이력 이동

완료 조건:

- 선택 집합과 전체 집합 실행 PASS
- 중지·timeout·429 모의시험 PASS
- 같은 TC의 중복 실행 방지와 재시도 이력 보존

사용자 액션:

- `일괄 TC 수행`에서 대표 Case 2~3건을 선택 실행하고 진행률·중지·결과 표시를 확인한다.
- 전체 35건 중 후속 Step 대상 9건이 `NOT_RUN`으로 표시되는 방식을 승인한다.
- 실제 26건 전체 실행 시점과 API 비용·소요시간을 결정한 뒤 Step 3 완료를 승인한다.

### Step 4. VOC 수행 이력 관리 — `COMPLETE`

목표:

- `홈 > 테스트 관리 > 테스트 수행 이력`과 유사한 VOC 전용 이력 화면을 제공한다.

구현 항목:

- `수행 이력` 메뉴
- 실행일시·실행 ID·유형·대상 수·PASS·FAIL·ERROR·성공률·Judge·배포 판정 목록
- 행 선택 상세 팝업 또는 상세 영역
- 케이스별 결과, Trace, Judge, 결함, 증적 다운로드
- 기간·상태·Judge·TC 필터
- 선택 삭제와 실행 폴더 동시 정리
- 원본 Run과 연결된 RETEST Run의 재시험 전후 비교
- Catalog·TC hash·Rubric 버전과 부모 Run 연결이 다르면 비교 차단

완료 조건:

- 수동·일괄 실행이 한 목록에 표시
- 삭제·필터·상세·재시험 전후 비교 테스트 PASS
- 이력과 실제 파일 수 불일치 검사 PASS

사용자 액션:

- 목록 필드·상세 화면·필터·삭제 범위와 보존 정책을 검토한다.
- 원본 Run과 연결된 RETEST Run 한 쌍을 지정해 재시험 전후 상태 비교를 확인하고 Step 4 완료를 승인한다.

### Step 5. 독립 LLM Judge — `COMPLETE`

목표:

- 수동·일괄 실행에서 선택적으로 독립 Judge를 수행한다.

구현 항목:

- Judge 사용 여부와 Judge 모델 선택
- 생성 모델과 Judge 모델 설정 분리
- JSON Schema 기반 100점 평가와 판정 근거
- malformed JSON, timeout, 429, 인증 오류 처리
- Judge 실패를 Pipeline 성공으로 위장하지 않는 상태 분리
- 모델·프롬프트·Rubric 버전, token·비용·시간 기록

독립성 등급:

- A: 생성 제공자와 Judge 제공자가 다름
- B: 제공자는 같지만 모델·프롬프트·호출 세션이 다름
- C: 같은 모델 계열로 편향 위험이 높아 사람 검토 필수

완료 조건:

- 수동 TC에서 Judge 선택 실행 PASS
- 일괄 실행에서 Judge 포함 집계 PASS
- Judge 비활성·실패·재시도 경로 PASS
- Evaluator·Critic 결과와 Judge 결과가 별도 보존됨

사용자 액션:

- 사용할 Judge Provider·모델과 API 자격 증명, 호출 비용 한도를 준비한다.
- 대표 Case의 Judge 결과·근거·독립성 등급을 검토하고 판정 임계값을 승인한다.

### Step 6. 최종 개선안 타당성 검증 — `COMPLETE`

목표:

구현 항목:

- VOC 원인 ↔ 근거 ↔ 개선 조치 ↔ 담당 ↔ 일정 ↔ KPI 추적표
- 타당성 자동 점수와 보완 요구사항
- QA 의견, 업무 담당자 의견, 승인·반려·보완 상태
- 승인자·시각·변경 이력
- 동일 질문·동일 TC·동일 Rubric 조건에서 기존 답변과 개선 답변의 실제 A/B 비교
- 독립 Judge 점수·타당성 점수·안전성·근거성 하락 여부를 함께 비교
- 안전성 하락 또는 근거 누락 시 강제 보류

`DRAFT → AI_REVIEWED → QA_REVIEWED → BUSINESS_APPROVED | REJECTED | REVISION_REQUIRED`

- 사람 승인과 반려 흐름 테스트 PASS
- 근거 없는 개선안·담당/KPI 없는 개선안 보류 테스트 PASS

사용자 액션:

- 시연에서는 동일인이 QA와 업무 역할을 각각 수행하되 두 단계의 의견과 시각이 별도 기록되는지 확인한다.
- 실제 `AI_PASS` 대표 개선안이 생성되면 QA 후 업무 승인 흐름을 시험한다.
- A를 선택해 연결 RETEST B를 생성하고 B만 선택하는 안내형 A/B 흐름을 확인한다.
