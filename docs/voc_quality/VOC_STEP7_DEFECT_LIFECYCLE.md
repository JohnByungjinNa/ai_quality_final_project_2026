페이지 상단의 중복 제목은 추가하지 않고 메뉴 경로 아래에서 바로 관리 구분을 선택하도록 구성했다.

## 3. 결함 저장 구조

- 전역 원장: `reports/voc_quality_defects/index.json`
- 결함 원본: `reports/voc_quality_defects/{DEFECT_ID}/defect.json`
- Run 역참조: `reports/voc_quality_runs/{RUN_ID}/defects.json`
- 결함 ID: `VOC-DEF-YYYYMMDD-HHMMSS-xxxx`
- 주요 필드: 심각도, 분류, 증적 상태, 관련 Run·Case·Trace, 원인, 영향, 조치, 담당자, 기한, Jira Key, 재시험 증적, 종료 근거, 전체 변경 이력

파일은 임시 파일 작성 후 교체하는 방식으로 저장하며, 결함 변경 시 관련 Run의 `defects.json`도 동기화한다.

## 4. 상태 전환 통제

허용 순서는 다음과 같다.

`OPEN → ANALYZED → FIXED → RETESTED → CLOSED`

- `ANALYZED`: 원인과 영향 필수
- `FIXED`: 조치 내용, 담당자, 조치 기한 필수
- `RETESTED`: 결함의 원본 Run을 부모로 하는 완료 RETEST 필수
- RETEST에는 결함 관련 Case가 모두 포함되어야 함
- 관련 Case는 요약 상태 또는 저장된 rule 결과가 모두 PASS여야 함
- `CLOSED`: 검증된 최신 PASS 재시험 증적과 종료 근거 필수
- 중간 상태 건너뛰기와 FAIL 재시험 연결은 차단

## 5. 후보 결함 등록

다음 2건을 실제 결함으로 단정하지 않고 `PENDING / OPEN` 후보로 등록했다.

| 후보 키 | 제목 | 심각도 | 증적 상태 | 현재 판단 |
|---|---|---:|---|---|
| `branch_interface_error` | 분기 인터페이스 오류 | HIGH | PENDING | 원본 FAIL Run·Trace 확인 필요 |
| `api_429_rate_limit` | API 429 장애 | HIGH | PENDING | 실제 429 응답·호출 로그 확인 필요 |

후보 상태에서는 확정 원인·조치·종료를 임의로 작성하지 않는다. 실제 증적이 확인된 경우에만 관련 Run·Case·Trace를 연결하고 `CONFIRMED`로 분석한다.

## 7. 사용자 확인 방법

1. 앱에서 `홈 > VOC 품질진단 > 장애·결함 관리`로 이동한다.
2. 결함 목록에서 두 후보가 `접수`, `HIGH`, `PENDING`으로 표시되는지 확인한다.
3. 후보가 확정 결함처럼 원인·조치 완료로 표시되지 않는지 확인한다.
4. 실제 증적이 있는 결함이 있다면 신규 등록에서 원본 Run과 Case를 연결한다.
5. 원인·영향을 입력해 분석 완료, 조치·담당·기한을 입력해 조치 완료로 전환한다.
6. 화면의 `관련 Case 재시험 시작`을 사용해 원본 Run에 연결된 RETEST를 실행한다.
7. FAIL이면 재시험 완료가 차단되고, PASS이면 재시험 완료 후 종료 근거를 입력할 수 있는지 확인한다.
8. 격리 장애시험에서 기존 6종 실행 기능이 유지되는지 확인한다.
