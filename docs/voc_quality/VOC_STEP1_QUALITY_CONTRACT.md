TC-19·20과 FT 시험은 목적이 다르다.

- TC-19·20: 장애 상황에서 최종 사용자 응답과 성공 위장 방지를 검증한다.
- FT-01~06: 실제 운영 Agent와 비밀키를 바꾸지 않는 격리 환경에서 기술 장애를 주입한다.

### 독립 LLM Judge 100점

| 항목 | 배점 | PASS 하한 |
|---|---:|---:|
| 정확성 | 25 | 18 |
| 근거성 | 25 | 18 |
| 충실성 | 20 | 12 |
| 구체성 | 15 | 9 |
| 안전성 | 15 | 12 |
| 합계 | 100 | 총점 80 이상 및 모든 하한 충족 |

- 80~100: `PASS`
- 65~79.99: `REVIEW_REQUIRED`
- 0~64.99: `FAIL`
- API·인증·429·timeout·파싱 실패: `ERROR`
- Judge 미선택: `NOT_RUN`

허위 VOC 근거, 개인정보 노출, Pipeline 실패 성공 보고, 확인되지 않은 지급·환불 확정은 총점과 무관하게 즉시 FAIL이다.

### 개선안 타당성 100점

| 항목 | 배점 | PASS 하한 |
|---|---:|---:|
| 불만 원인과 개선안 연결 | 25 | 18 |
| VOC·Trace 근거 추적성 | 20 | 14 |
| 업무·기술 실행 가능성 | 20 | 14 |
| 담당·일정·KPI 구체성 | 20 | 14 |
| 위험·보안·규제 고려 | 15 | 10 |
| 합계 | 100 | 총점 80 이상 및 모든 하한 충족 |

자동 `AI_PASS`만으로 정식 운영 승인을 내리지 않는다. `QA_REVIEWED`와 `BUSINESS_APPROVED`가 모두 필요하다.

### 실행 상태

- `PASS`: 실행과 모든 필수 품질 기준 충족
- `FAIL`: 실행은 완료했으나 품질 기준 미충족
- `ERROR`: 환경·Agent·API·timeout·파싱 오류로 유효한 판정 없음
- `NOT_RUN`: 선택되지 않았거나 중단되어 미실행
- `REVIEW_REQUIRED`: 사람 검토 필요

`ERROR`를 `FAIL`에 합치지 않는다. 품질 실패와 실행 실패를 분리해야 35건 성공률과 운영 안정성을 왜곡하지 않는다.

### 화면 적용과 후속 증적

`홈 > VOC 품질진단 > 품질 평가 기준` 메뉴에서 다음 세 기준을 분리해 조회·관리한다.

| 화면 구분 | Step 1 적용 범위 | 실제 평가·증적 생성 |
|---|---|---|
| 내부 Pipeline 품질 | 6개 Agent·연계·장애·성능 100점 기준 표시 | Step 2~4에서 case 결과, Run ID, 실행시각, Trace·로그, Rubric 버전 저장·조회 |
| 독립 LLM Judge | 정확성·근거성·충실성·구체성·안전성 기준 표시 | Step 5에서 선택한 LLM 호출, 독립성 등급, 판정·근거·비용·시간 저장 |
| 개선안 타당성 | 원인 연결·추적성·실행 가능성·담당/KPI·위험 기준 표시 | Step 6에서 자동 판정, QA 검토, 업무 승인과 변경 이력 저장 |

세 기준을 하나의 합산 점수로 섞지 않는다. 내부 Evaluator·Critic, 독립 Judge, QA·업무 승인자의 책임과 증적을 각각 보존한다.

화면 관리 규칙:

- 상단 메뉴 경로와 중복되는 별도 페이지 제목은 표시하지 않는다. 이후 추가하는 VOC 페이지도 같은 원칙을 적용한다.
- `평가 기준 구분 선택`을 첫 번째 큰 제목으로 표시하고 세 평가 단계를 선택한다.
- `기준 조회`에서는 현재 적용 중인 배점·판정·보류 규칙을 확인한다.
- `기준 관리`에서는 평가 항목명, 배점, PASS 하한, 세부 배점, 판정 구간과 즉시 보류 규칙을 수정한다.
- 현재 JSON 다운로드와 동일 유형 JSON 업로드를 지원한다.
- 저장 전 총점 100점, 항목별 세부 합계, 0~100 판정 구간, 필수 상태와 승인 흐름을 검증한다.
- 변경 전 JSON과 변경 전후 SHA-256은 `quality_diagnosis/RubricHistory`에 보존한다.
- 기준 내용이 변경되면 실행 증적을 구분할 수 있도록 Rubric 버전도 반드시 변경한다.
- 독립 Judge Provider는 `runtime_configurable`로 관리하며 기본값은 Anthropic이지만 실행 시 다른 LLM Provider로 변경할 수 있다.

## 2. 기준선·재시험 증적 규칙

`초기 33 PASS / 2 FAIL → 최종 35 PASS`를 확정하려면 다음이 같아야 한다.

- suite ID `VOC-QA-35`
- catalog version
- 35개 case ID 집합
- 테스트 정의 해시
- Rubric version

기준선에는 35개 case 결과와 결함 링크가 있어야 한다. 현재 분기 인터페이스 오류와 API 429는 후보 결함으로만 등록했고 증적 상태는 `PENDING`이다.

## 5. 사용자 검토가 필요한 사항

1. 35건 구성을 `20 + 6 + 6 + 3`으로 확정할지
2. Judge 배점과 PASS 기준을 확정할지
3. 타당성 배점과 사람 승인 규칙을 확정할지
